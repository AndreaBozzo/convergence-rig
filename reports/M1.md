## Limitations

- Single-host Windows 11 Docker Desktop numbers are specific to this machine's container I/O and fsync latency (~15 ms median commit); they are baseline reference measurements for M2's matched pair on this host, not general benchmark claims.
- Automatic compaction in `pg2iceberg` remained disabled (`target_file_size: 0`). Steady-state probe visibility lag increased gradually from `9.82 s` (probe 1, 6 data files and 2 equality-delete files) to `13.19 s` (probe 8, 20 data files and 16 equality-delete files), reflecting both `pg2iceberg`'s ~10 s materializer cycle and DuckDB reading uncompacted delete files.
- The 25,000-row table (`~7.5 MB` total relation size after seed, `~9.5 MB` after workload) may be fast for PostgreSQL 19 `REPACK (CONCURRENTLY)` to rewrite in M2; per the plan, M2 may need a larger `--seed-rows` count for both members of the matched pair if REPACK finishes too quickly to observe write overlap.
- Running `uv run pytest` inside a restricted Windows sandbox emits a `PytestCacheWarning` when creating `.pytest_cache`; all 20 tests pass cleanly.

## Open questions

- In M2, will `25,000` rows (`~9.5 MB`) produce a measurable `REPACK (CONCURRENTLY)` overlap window at `10.0 ops/s`, or should both members of the matched pair scale up (for example to 150,000 to 250,000 rows)?
- Should M2 keep `target_file_size: 0` (to stay directly comparable to M1 and avoid compaction noise during REPACK) or test compaction separately once the matched pair result is established?
