# Milestone M3 Report: Repeat and Report

**Verdict:** `pass` (all `3/3` baseline runs `converged`, all `3/3` concurrent REPACK runs `converged`, plain REPACK control `converged`; counterbalanced order `baseline-first`, `repack-first`, `baseline-first`; all `7` runs passed exact schema and ~250,000-row verification on their first marker-bearing Iceberg snapshot)

Three fresh counterbalanced matched pairs on the 250,000-row fixture (`25,000` out-of-line TOAST rows, `180 s` at `10.0 ops/s`, matched seed within each pair) confirmed the M2 result reproducibly. Every concurrent `REPACK (CONCURRENTLY) public.orders` run rewrote heap, TOAST and primary-key relation files while `43` to `48` writes committed concurrently (`median 43.0 ops`), temporarily raised the `pg2iceberg_slot` confirmed-flush WAL gap to ~`401.8 MB`, drained cleanly, and converged to an exact row, value, and schema match in DuckDB (`0` source-only, `0` lake-only, `0` duplicate IDs, `0` value mismatches). Across the three pairs on this host, concurrent REPACK added a consistent median `+11.76 ms` (`[+7.55, +14.04] ms`) to matched-interval median execution latency (`31.65 ms` vs `19.38 ms`) while keeping full-window median execution latency virtually unchanged (`+0.21 ms`, `[-0.35, +0.26] ms`) and recording `0` blocked lock waiters. A single fresh plain `REPACK public.orders` control run on Pair 1's seed (`20261119`) confirmed that the `50 ms` sampler catches `AccessExclusiveLock` (`47/47` samples, `4,219.7 ms` span) and blocked writers (`46` waiter samples, `4,215.8 ms` peak scheduled-to-completed latency, `44` missed-schedule ops), establishing a clear empirical contrast with concurrent REPACK while also converging cleanly.

Key performance takeaways on this host:
- **Consistent median slowdown during REPACK:** Across all three pairs (and M2's `+9.21 ms`), concurrent REPACK raised matched-interval median execution latency by `+7.55` to `+14.04 ms` (`median +11.76 ms`), reflecting concurrent disk/WAL I/O during the ~4.4 s rewrite.
- **No order bias:** Pair 2 (`repack-first`) showed the same `+14.04 ms` matched-interval median execution delta and `0` blocked waiters as Pairs 1 and 3 (`baseline-first`).
- **Tail latency noise vs REPACK:** Full-window p99 and max latencies (`166` to `542 ms`) overlap broadly between baseline and concurrent REPACK because container fsync/checkpoint pauses dominate the host's tail. Every `missed_schedule_count > 0` occurred with `harness_missed_arrival_count = 0` (server commit backpressure, not harness drift).
- **Reader lag unaffected:** Steady-state DuckDB probe lag (`p50` `8.2` to `11.0 s`, `max` `14.0` to `15.5 s`) and final-marker commit-to-visibility (`7.8` to `11.0 s`) stayed governed by `pg2iceberg`'s ~10 s materializer cycle rather than by REPACK.

## Limitations

- Single-host Windows 11 Docker Desktop environment: latency distributions and ~`4.2-4.8 s` rewrite times apply to this machine and storage stack only.
- Automatic compaction in `pg2iceberg` remained disabled (`target_file_size: 0`), keeping all `17` equality-delete files live on every tested snapshot.
- Only `30 s` of workload (~`300` writes) preceded REPACK, so reclaimed space was modest (`-114.7 KB` to `-573.4 KB` for concurrent REPACK, `-811.0 KB` for plain REPACK). Heavily bloated tables and clustering with `USING INDEX orders_pkey` were not exercised.
- At `10.0 ops/s`, the brief final `AccessExclusiveLock` during `performing final cleanup` always landed inside a `100 ms` inter-arrival gap, so concurrent-REPACK final-lock contention at higher arrival rates (e.g., `100+ ops/s` or multi-connection writers) was not tested.
- This lab verifies final-state convergence and steady-state marker visibility; it does not assert that every intermediate update version appeared as its own distinct Iceberg snapshot.
