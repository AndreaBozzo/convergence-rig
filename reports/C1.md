# Milestone C1 Report: REPACK Pairs with pg2iceberg Compaction Enabled

**Verdict:** `pass` (`6/6` valid runs `converged`; `3/3` baseline runs and `3/3` concurrent REPACK runs across counterbalanced orders `baseline-first`, `repack-first`, `baseline-first` on M3 seeds `20261119`, `20261120`, `20261121`; compaction proved from Iceberg snapshot metadata inside the measurement window in all `6/6` runs; `0` conflicts, retries or errors in `pg2iceberg.log`; side-by-side comparison with M3 reproduced byte-for-byte from raw files)

Enabling automatic compaction in `pg2iceberg 0.12.0` (`compose/pg2iceberg.compaction.yaml`, selected via `PG2ICEBERG_CONFIG_FILE`) did not break exact CDC convergence during concurrent PostgreSQL 19 `REPACK (CONCURRENTLY) public.orders`. Every run executed `13` to `14` Iceberg `replace` (`pg2iceberg.operation=compaction`) commits inside the 180 s measurement window (`11-12` small-file merges plus `2` full delete-retiring rewrites that each replaced `5` data files with `3` clean files and retired `6` equality-delete files), reducing verified-snapshot file counts from M3's `43` data files and `17` equality-delete files (`1,542` deletes) to `4-5` data files and `5` equality-delete files (`447-461` deletes). In all three REPACK runs, a compaction commit landed inside the REPACK window (`seq=30`) and two compaction spans overlapped REPACK; in all six runs, a small-file compaction commit landed between the final-marker commit and the verified append snapshot (`seq=56` or `57`, direct parent of `verified_snapshot_id`). All six runs matched PostgreSQL 19.0 row for row on their first marker-bearing snapshot (`0/0/0/0` diffs, `schema_id=0`), with zero errors, conflicts or retries in `pg2iceberg.log`. Against M3 on the same seeds, DuckDB full-diff duration fell from median `22,846.31 ms` to `10,032.10 ms` (`-12,572.74 ms`, `-55%`), while the within-pair REPACK matched-interval write-latency delta stayed consistent (`+10.81 ms` in C1 vs `+11.76 ms` in M3). Project-only cleanup left `0` `cdclab` containers, volumes or networks after every run and left all `14` unrelated host containers unchanged.

Interpretation of the C1-vs-M3 deltas:
- **Direct compaction effect (file layout and reader scan speed):** Cutting live files from `43` data + `17` equality-delete files to `4-5` data + `5` equality-delete files reduced DuckDB full-diff duration by more than half (`22.85 s -> 10.03 s`) and tightened worst-case steady-state probe lag (`max 14.78 s -> 13.59 s`). Final-marker visibility also dropped (`10.04 s -> 3.96 s`), reflecting both faster DuckDB scans on fewer delete files and materializer cycle phase alignment at `t=180 s`.
- **Host session effect (writer latency and REPACK duration):** Baseline PostgreSQL write latency (`5.14 ms` in C1 vs `14.38 ms` in M3) and REPACK duration (`2.18 s` in C1 vs `4.37 s` in M3) were faster during the C1 session (run ~4 hours after M3 on the same Windows 11 Docker Desktop host). This reflects host disk/fsync load variation across sessions rather than an effect of Iceberg compaction on PostgreSQL writes. The within-pair REPACK slowdown (`+10.81 ms` in C1 vs `+11.76 ms` in M3) remained consistent across both sessions.
- **No reader-lag regression from background compaction:** Steady-state probe median lag remained governed by the `10 s` materializer cadence (`10.70 s` in C1 vs `10.21 s` in M3), with cumulative compaction work totaling `3.91` to `6.62 s` across `15-16` passes per run.

## Limitations

- Single-host Windows 11 Docker Desktop environment; M3 and C1 ran ~4 hours apart, and host fsync throughput differed between the two sessions (`5.14 ms` vs `14.38 ms` baseline write median, `2.18 s` vs `4.37 s` REPACK duration). Cross-session absolute write latency comparisons should therefore be read with that host variance in mind, whereas within-pair REPACK deltas and Iceberg file/diff improvements are directly comparable.
- `compaction_data_files` (`4` vs default `8`) and `compaction_delete_files` (`6` vs default `32`) were lowered to guarantee repeated small-file and delete-retiring compaction inside a 180 s window at `10 ops/s`. A longer soak run (e.g. 15-30 minutes) would be needed to exercise the upstream defaults (`8` / `32`).
- In all three REPACK runs, the compaction commit landing inside the REPACK window (`seq=30`) was a small-file merge (`~0.7 MB`), whereas the two full `345 MB` delete-retiring compactions occurred later (`seq=38` around `t=74 s` and `seq=49` around `t=139 s`). An overlap between REPACK and a full `345 MB` delete-retiring compaction was not triggered under `repack_delay_s=30 s`.
- Compaction ran inside single-process `pg2iceberg run` (single committer). Concurrent out-of-band `pg2iceberg compact` (separate process racing the materializer for catalog commits) was not tested in this milestone.
