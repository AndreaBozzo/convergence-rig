# Milestone K2 Report: Catalog Metadata Restore Drill

**Verdict:** `pass` (drill outcome: `mismatch at deadline`; silent data loss reproduced with `209` diverged rows across `302` skipped CDC offsets and `0` errors in `pg2iceberg.log`; documented `pg2iceberg 0.12.0` re-snapshot recovery restored `converged` exact match `25,041 = 25,041` in `21.18 s`)

Restoring Lakekeeper's PostgreSQL catalog database (`lakekeeper-db`) from a `pg_dump` taken `39.26 s` into the M1 `25,000`-row, `10.0 ops/s` workload rolled the Iceberg catalog back by `3` committed snapshots (`seq=11 -> seq=8`, `pg2iceberg.log-end` `688 -> 386`) while `_pg2iceberg.mat_cursor` in PostgreSQL stayed at `688` and Silo kept all `93` pre-restore objects intact. `pg2iceberg 0.12.0` remained running across the `3.29 s` restore window, logged zero errors and zero warnings, and silently forked the Iceberg table history on its next cycle by committing a new `seq=9` snapshot (`parent=seq=8`, `log-start=688..789`). That silent continuation skipped offsets `(386, 688]` (`302` staged CDC operations) permanently, even though the staged Parquet files and `_pg2iceberg.log_index` rows remained intact. At the end of the 180 s workload, the final marker (`900999999`) became visible in `3.94 s`, and both the independent DuckDB exact verifier (`lab/compare.py`) and `pg2iceberg verify` (`exit code 1`) detected the exact same `209` diverged rows (`39` rows lost from Iceberg while still in PostgreSQL, `48` deleted rows resurrected in Iceberg, `122` stale rows including `6` hybrid TOAST corruptions where post-restore unchanged-TOAST updates merged current scalar columns with pre-dump TOAST blobs). Executing the documented `pg2iceberg 0.12.0` recovery (`stop` -> `pg2iceberg cleanup` -> Lakekeeper `DELETE` table -> `pg2iceberg snapshot` -> `pg2iceberg run`) rebuilt the mirror and replicated post-recovery mutations cleanly, passing both exact verification (`25,041 = 25,041`, `0/0/0/0` diffs, `schema_id=0`) and `pg2iceberg verify` (`exit code 0`). Project-only cleanup left `0` `cdclab` resources and left all `14` unrelated host containers unchanged.

Raw evidence is committed under [runs/20261120T122551Z-k2-catalog-restore-drill/](../runs/20261120T122551Z-k2-catalog-restore-drill/). A local upstream note on `pg2iceberg`'s silent skip on catalog rollback is drafted at [drafts/pg2iceberg-catalog-rollback-silent-skip.md](../drafts/pg2iceberg-catalog-rollback-silent-skip.md).

- All **`209` remaining IDs** (`209 / 209 = 100%`) appeared in the exact diff:

**Hybrid TOAST corruption detail (`6` rows: `id=19, 29, 43, 84, 89, 110`):** On these `6` rows, `amount`, `status`, `updated_at`, and `discount` matched PostgreSQL's post-restore values, while only `note` and `payload` differed. Each row received `update_toast_changed` inside the rolled-back window (for example `id=19` moving `rev=0 -> rev=1`) followed by `update_toast_unchanged` after the restore. Because `REPLICA IDENTITY DEFAULT` omits unchanged TOAST columns from logical WAL, `pg2iceberg` preserved the stale pre-dump TOAST blobs (`rev=0`) from the rolled-back Iceberg table alongside the post-restore scalar columns, materializing a hybrid row that never existed in PostgreSQL.

This fills in the L3 design note with concrete failure modes proved in K1 and K2.

#### What must be backed up together, and in what order

A catalog-only backup (`lakekeeper-db` alone) is insufficient for a running CDC pipeline because `pg2iceberg` keeps its commit cursor (`_pg2iceberg.mat_cursor`, `_pg2iceberg.log_index`, `pg2iceberg_slot`) in the source PostgreSQL database while Lakekeeper keeps the Iceberg snapshot pointer in `lakekeeper-db` and the Parquet/Avro/metadata JSON files live in object storage. As K2 proved, restoring `lakekeeper-db` to an earlier point without coordinating `pg2iceberg` causes silent data loss and timeline forking.

**Coordinated backup order (for a consistent point-in-time recovery set):**
1. **Object storage durability first (continuous):** Enable bucket versioning / object retention (longer than the catalog backup retention window) on the warehouse bucket so no referenced `data/`, `metadata/`, or `staged/` objects are deleted while backups can still point to them. Do not run short-retention orphan cleanup before confirming backup retention bounds.
2. **Encryption key and authz state (durable secret store):** Back up `LAKEKEEPER__PG_ENCRYPTION_KEY` (and Keycloak realm/clients + `openfga-db` if authorization is enabled) alongside catalog backups; `lakekeeper-db` credentials are unusable without `LAKEKEEPER__PG_ENCRYPTION_KEY`.
3. **Catalog Postgres (`lakekeeper-db`) with PITR (base backup + continuous WAL archiving):** Take consistent `lakekeeper-db` backups (`pg_basebackup` + WAL archiving, not point-in-time `pg_dump` alone) so the catalog can be recovered to the latest committed transaction rather than rolling back behind `pg2iceberg`.
4. **Source PostgreSQL + `_pg2iceberg` coordinator state (recorded, not rolled back independently):** Record `_pg2iceberg.mat_cursor`, `_pg2iceberg.log_seq`, and `pg2iceberg_slot` LSNs; remember that source PG is the operational system of record and is never rolled back to match a stale catalog backup.

**Coordinated restore order (when `lakekeeper-db` must be restored):**
1. **Stop `pg2iceberg` (and all other Iceberg writers) BEFORE starting the restored Lakekeeper.** K2 showed that leaving `pg2iceberg` running while a stale `lakekeeper-db` comes back immediately forks the table timeline and permanently skips `(restored_log_end, mat_cursor]`.
2. **Restore `lakekeeper-db` (plus `openfga-db` if authz is enabled) to the latest possible WAL point** using the backed-up `LAKEKEEPER__PG_ENCRYPTION_KEY`, run `lakekeeper migrate`, and start `lakekeeper serve` with writers still stopped.
3. **Compare Lakekeeper's restored `pg2iceberg.log-end` against `_pg2iceberg.mat_cursor` and object storage BEFORE resuming `pg2iceberg`:**
   - **Case A (no writer forked yet, newer `v*.metadata.json` still exists in object storage matching `mat_cursor`):** Unregister the stale table (`DELETE ...?purgeRequested=false`) and re-register the latest `metadata.json` from object storage via Iceberg REST `POST /v1/{prefix}/namespaces/{ns}/register`, verify `pg2iceberg.log-end == mat_cursor`, then start `pg2iceberg`.
   - **Case B (metadata files are also missing, or a writer already forked the table as in K2):** Run the documented `pg2iceberg cleanup` -> drop diverged Iceberg table -> `pg2iceberg snapshot` -> `pg2iceberg run` procedure, verify with `pg2iceberg verify` and an independent reader diff, then purge the old table UUID prefix from object storage.
4. **Post-restore verification:** Run `pg2iceberg verify` plus an independent DuckDB/Spark snapshot comparison and (if authz is enabled) scoped-access deny checks before declaring recovery complete.

## Limitations

- Tested with `pg_dump` / `pg_restore` into a freshly recreated `lakekeeper` database inside the running `lakekeeper-db` container (simulated backup restore with a 30 s RPO gap) rather than a physical volume replacement with PostgreSQL PITR WAL replay.
- Only one documented recovery path (`pg2iceberg cleanup` -> Lakekeeper `DELETE` table -> `pg2iceberg snapshot` -> `pg2iceberg run`) was executed. The alternate Lakekeeper `POST .../register` path (re-registering the pre-restore `00009-...gz.metadata.json` *before* allowing `pg2iceberg` to commit and fork) was not executed separately because K2 required keeping `pg2iceberg` running across the restore, which forked the timeline immediately.
- `target_file_size` stayed `0` (matching M1); enabling compaction would add `replace` snapshots to the rolled-back and forked branches but does not change `mat_cursor > iceberg_log_end`.
- `DELETE .../tables/orders?purgeRequested=false` left `215` objects under the old diverged table UUID prefix in Silo; testing `purgeRequested=true` (asynchronous `tabular_purge`) and verifying full prefix reclamation was not run here.

## Open questions and gaps noticed

- **Upstream gap (`pg2iceberg 0.12.0`):** The materializer fast-forwards `mat_cursor` when Iceberg `pg2iceberg.log-end` is ahead of PostgreSQL, but has no guard when `pg2iceberg.log-end` is behind `mat_cursor`. A strict `iceberg_log_end < mat_cursor` check would turn silent data corruption and hybrid TOAST rows into a loud, actionable error before the table timeline is forked. See [drafts/pg2iceberg-catalog-rollback-silent-skip.md](../drafts/pg2iceberg-catalog-rollback-silent-skip.md).
- **Pre-fork `registerTable` recovery path:** If operators stop `pg2iceberg` before starting a restored `lakekeeper-db`, testing whether Lakekeeper's `DELETE ?purgeRequested=false` + `POST .../register` on the latest pre-restore `metadata.json` recovers zero-loss CDC without a full re-snapshot is a worthwhile follow-up drill for large tables.
