# Milestone R2 Report: Minimal Reproduction of the Silent Skip After a Catalog Restore

**Verdict:** `pass`. Three of three clean runs per image printed the same `RESULT:` line and exited with code `1`, for `polynyadev/pg2iceberg:0.12.0` and for `polynyadev/pg2iceberg:sha-4344888` (main at `4344888eb6`). Main still skips silently: it records `pg2iceberg.log-ends` in the table properties, but it only compares that record with the cursor in the direction "catalog ahead of cursor". A catalog behind the cursor is not checked.

The reproduction is in [repro/pg2iceberg-catalog-restore/](../repro/pg2iceberg-catalog-restore/) (`docker-compose.yml`, `pg2iceberg.yaml`, `repro.sh`, `README.md`). It uses Compose project `p2irestore`, ports on `127.0.0.1` (`35432`, `38181`, `39000`, none used by `cdclab` or `p2irepro`), only public images pinned by digest, and POSIX `sh`, `curl`, `awk` and `sed`. A table of 35 rows and seven transactions is enough; a run takes about one minute.

Raw evidence: [runs/20261120T143910Z-r2-catalog-restore-repro/](../runs/20261120T143910Z-r2-catalog-restore-repro/) (`summary.txt`, one log per run, the `pg2iceberg` and `lakekeeper` container logs of each run, `final_down.log`, and `development/`).

## What main does

Pinned source: `git clone https://github.com/polynya-dev/pg2iceberg.git upstream/pg2iceberg-4344888` and `git checkout 4344888eb6` (HEAD `4344888eb64e3edc44d081dd8d721ce8f0c618a3`, 2026-11-17, `upstream/` is gitignored). The same function is unchanged from `v0.12.0` apart from line numbers.

Main writes the per-group end of the applied log into the table property `pg2iceberg.log-ends` and into each snapshot summary (`crates/pg2iceberg-iceberg/src/lib.rs`, `crates/pg2iceberg-iceberg/src/prod/catalog.rs`; `docs/architecture/maintenance.md` line 42). It reads the value in one place in the cycle, `Materializer::begin_unit`, `crates/pg2iceberg-logical/src/materializer.rs` line 2925:

```rust
async fn begin_unit(&mut self, ident: &TableIdent, unit: &mut Unit, start: u64) -> Result<()> {
    unit.start_offset = Some(start);
    // The index is untouched since `index_at`.
    let applied = self.sync_file_index(ident).await?;
    if let Some(&end) = applied.get(&self.unit_group(unit)) {
        if end > start {
            return Err(MaterializerError::AlreadyApplied { end });
        }
    }
    Ok(())
}
```

`start` is the first staged log entry past the cursor. `AlreadyApplied` is handled in `apply_table` (line 2767): it moves the cursor to `end` and goes on. There is no branch for `end < start`, and no check at start-up. The only other readers of `log_ends` are the commit-failure path (line 3194) and `sync_file_index`, which returns the map to `begin_unit`. The second guard, `log_continues` (line 2788, error `LogGap`), compares the cursor with the first staged log entry, so it only catches a log that was truncated past the cursor. `docs/architecture/materializer.md` line 31 describes the same one-sided check: "if a commit already applied past it, it moves the cursor there and goes on from the end."

The runs agree with the code: `log-ends` in the restored table is `{"default":6}`, `start` is `29`, `6 > 29` is false, the unit commits, and the table's `log-ends` becomes `{"default":31}`.

## Choices that differ from the plan text, and why

- The backup is taken after the first snapshot and after a second one. The first snapshot (the initial table copy) carries no `pg2iceberg.log-start` or `log-end`, so restoring to it would show no recorded end. One small change (5 rows) is committed first, so the backup holds a snapshot with `log-end 6`, as in K2.
- The check "backup after the first snapshot, at least two more snapshots before the restore" is in the script and exits `2` with `RESULT: invalid run (...)` if it fails. It also checks that the catalog did not change while the dump ran, that the cursor is ahead of the backup, that every staged change is committed before the restore (cursor, end of the staged log and snapshot `log-end` equal), that the catalog really returned to the backed-up snapshot, and that pg2iceberg is still running after the restore.
- `materializer_interval` is `8s` (`flush_interval` `2s`), and the restore starts when the last change is committed, so the 3 s restore window falls between two materializer cycles. This avoids the R1 exit of `0.12.0` on a catalog outage, which would make a run depend on timing. If pg2iceberg does exit during the window, the run is invalid (exit `2`).
- The final line carries only categories and the exit code of `verify`. The offsets and diff counts are printed on `DETAIL:` lines, because they depend on batching.
- `P2I_CONTROL=1` (no restore) was added so the detector is seen passing as well as failing.

## Failed attempts kept on record

In [development/](../runs/20261120T143910Z-r2-catalog-restore-repro/development/):

1. `failed-attempt1-msys-path.log`: `psql -f /tmp/lakekeeper.sql` run through `docker exec` from Git Bash had its path rewritten to `C:/Users/.../Temp/lakekeeper.sql` (`No such file or directory`), after the old database had already been dropped. Fixed by running the restore inside `sh -c '...'`.
2. `failed-attempt2-verify-msys-path.log`: the same path rewriting broke `verify --config /etc/pg2iceberg/config.yaml` (`C:/Program Files/Git/etc/...`), so `verify` exited `1` for the wrong reason and the script still printed `verify reported diffs`. Fixed with `MSYS_NO_PATHCONV=1` in `repro.sh`, and the script now exits `2` when `verify` fails without a `diff detected` line.
3. The first `up` started pg2iceberg together with the base services because the profile was active, and it exited (no log kept); the base services are now named explicitly.
4. `main-before-control-flag.log` and `0.12.0-before-control-flag.log` are full runs of the script before the control switch and the final apply-wait were added; both printed the same `RESULT:` line.

## Limitations

- One host (Windows 11, Docker Desktop, Git Bash, `amd64`). Not run on Linux or macOS; the images are multi-arch index digests and the script is checked with `sh -n` and POSIX-only syntax, but BSD `awk` and `sed` are untested.
- A single table with a primary key, no TOAST columns, one catalog (Lakekeeper `v0.15.1`). K2 covered the TOAST hybrid rows; they are not in this repro.
- The restore is a `DROP DATABASE` and `pg_dump` restore into a stopped Lakekeeper, like K2, not a point-in-time recovery of a managed database.
- R2 did not check whether the staged log and `_pg2iceberg.log_index` still hold the skipped range on main. K2 showed that on `0.12.0`. A replay fix depends on it.
- The offsets (`6`, `29`) are batch counts of staged log entries, not row counts.

## Gaps noticed

- Neither `0.12.0` nor main exposes the "recorded end behind the cursor" state in `/healthz`, `/readyz`, metrics or logs, so an operator cannot alert on it. The R2 script computes it from the catalog and `_pg2iceberg.mat_cursor`.
- R1's split mode was not run against a catalog restore. `stream-only` plus `materializer-only` share the cursor in the same way, so the same gap is expected, but it was not tested.
