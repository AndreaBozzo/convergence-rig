# Milestone L3 Report: Catalog Outage Drill

**Verdict:** `pass` (Run 1 unsupervised outcome: `mismatch at deadline`; Run 2 with connector restart after catalog recovery outcome: `converged`, exact `25,039`-row and schema match)

Stopping Lakekeeper for `60 s` during the M1 `25,000`-row, `10.0 ops/s` baseline workload exposed an important operational behavior of `pg2iceberg 0.12.0` in single-process `run` mode. In both fresh runs, `pg2iceberg` continued staging WAL changes to Silo and `_pg2iceberg.log_index` for ~`9.4` to `10.1 s` using its cached vended S3 credentials (`+5` staged log files, `161` pending unapplied offsets) and uploaded `2` uncommitted Iceberg Parquet files, then exited fatally with code `1` on its first `materializer.cycle()` catalog HTTP request (`Error: logical lifecycle ... materializer.cycle: catalog: other: Unexpected => Failed to execute http request`). Without a supervisor or connector restart (Run 1), `pg2iceberg_slot` remained inactive after Lakekeeper returned and the run ended in `mismatch at deadline`. When `pg2iceberg` was restarted after Lakekeeper became healthy (Run 2), it resumed cleanly from both `_pg2iceberg.log_index` (`589 -> 750`) and the retained WAL on `pg2iceberg_slot` (`1,771,944` bytes confirmed-flush gap, `1,772,544` bytes restart gap), committed its first post-outage snapshot in `14,070.60 ms` (`13,630.53 ms` from connector restart), drained the full outage backlog in `15,725.09 ms`, returned steady-state probe lag to ~`10 s`, and converged on the first final-marker snapshot (`5721944575849070880`) with `25,039 = 25,039` exact rows (`0` source-only, `0` lake-only, `0` duplicate IDs, `0` value mismatches). Project-only cleanup left `0` `cdclab` containers, volumes or networks and left all `14` unrelated host containers unchanged in both runs.

### 2. Connector behavior, backlog mechanics and orphan files

Evidence: [Run 1 pg2iceberg.log](../runs/20261119T210838Z-l3-catalog-outage/pg2iceberg.log), [Run 2 pg2iceberg.log](../runs/20261119T212047Z-l3-catalog-outage-recovery/pg2iceberg.log), [Run 2 outage_samples.jsonl](../runs/20261119T212047Z-l3-catalog-outage-recovery/outage_samples.jsonl), [Run 2 duckdb_snapshots_final.json](../runs/20261119T212047Z-l3-catalog-outage-recovery/duckdb_snapshots_final.json).

- **Phase 1 (first ~10 s of catalog outage):** `pg2iceberg` kept reading WAL from `pg2iceberg_slot`, uploading `5` staged Parquet log batches to Silo (`+375` to `+400 KB`) using its cached vended S3 object store, recording them in `_pg2iceberg.log_index` (`34 -> 39` rows, `161` unapplied offsets), and advancing `confirmed_flush_lsn`.
- **Phase 2 (materializer failure and process exit):** On its next `10 s` materializer cycle, `pg2iceberg` folded staged events, uploaded `2` Parquet files (`1` data file + `1` equality-delete file, `+358.5 KB` in Run 2) to Silo, and attempted to load/commit table metadata on Lakekeeper. Because Lakekeeper was stopped, `materializer.cycle()` failed with:
  ```text
  Error: logical lifecycle

  Caused by:
      0: materializer.cycle: catalog: other: catalog: other: Unexpected => Failed to execute http request, source: error sending request for url (http://lakekeeper:8181/catalog/v1/01a1f5af-2b97-7641-9815-44df843a077b/namespaces/public/tables/orders)
  ```
  Verified in `pg2iceberg v0.12.0` (`crates/pg2iceberg-validate/src/runtime.rs:1404`), `Ticks::finish` treats any `materializer.cycle()` error as fatal in single-process `run` mode, exiting with code `1` (unlike `run_materializer_only` in `crates/pg2iceberg/src/run.rs:478-484`, which logs a warning and retries).
- **Phase 3 (remaining ~50 s of outage):** With `pg2iceberg` exited, `pg2iceberg_slot` remained durable but inactive (`active=false`), retaining `~1.74-1.77 MB` of WAL over the remaining outage window while source writes continued at `10.0 ops/s` with normal latency (`p50=11.74 ms` exec, `0` errors).
- **Phase 4 (recovery in Run 2):** After Lakekeeper returned healthy (`1,552.40 ms` from `docker compose start lakekeeper`), starting `pg2iceberg` logged `"replication slot exists, resuming"`, reconnected cleanly without re-snapshotting, and committed two back-to-back catch-up snapshots:
  - Snapshot `seq=11` (`1309864078799033903`, `13.63 s` after connector restart): applied `pg2iceberg.log-start=589..750` (`161` pre-crash staged offsets, `118` added records, `124` equality deletes).
  - Snapshot `seq=12` (`2677826451300447874`, `189 ms` later): applied `pg2iceberg.log-start=750..1416` (`666` replayed WAL + live offsets, `452` added records, `441` equality deletes), making in-outage Probe 5 (`id=900000005`) visible in `29.21 s` from commit.
- **Orphan file footprint:** At the end of Run 2, Silo held `30` objects (`10,360,780 B`) under `data/`, whereas Iceberg metadata (`duckdb_final_metadata_summary`) referenced `28` live files (`16` data + `12` equality-delete = `10,002,255 B`). The exact `2`-file (`358,525 B`) difference is the uncommitted data + equality-delete pair uploaded right before the outage crash, confirming that periodic orphan-file cleanup is needed after catalog outages. Silo also retained `63` `pg2iceberg_staging` objects (`4,562,083 B`) matching `log_index_row_count=63`.

## Metadata restore drill and operations owner list (design notes, no restore executed)

Per `docs/PLAN.md`, self-hosting Lakekeeper for a critical workflow requires a tested metadata restore drill and explicit operational ownership before production adoption.

### What a Lakekeeper metadata restore drill would need

1. **Backup scope and consistency:** Scheduled PostgreSQL base backups plus continuous WAL archiving (PITR) for `lakekeeper-db` (and `openfga-db` when authorization is enabled), plus durable backup of `LAKEKEEPER__PG_ENCRYPTION_KEY` (stored credentials in `lakekeeper-db` cannot be decrypted without it) and the OpenFGA authorization model/tuples.
2. **Drill sequence (in an isolated restore target):**
   - Quiesce writers or record the exact current Iceberg `metadata-location` pointers before simulating catalog DB loss.
   - Restore `lakekeeper-db` (and `openfga-db`) from backup to a clean Postgres instance with the backed-up `LAKEKEEPER__PG_ENCRYPTION_KEY`, run `lakekeeper migrate`, and start `lakekeeper serve`.
   - Reconcile any Iceberg metadata pointer drift: if snapshots were committed to S3 *after* the restored catalog DB point-in-time (split-brain / RPO gap), identify the latest `v*.metadata.json` in object storage, verify whether `pg2iceberg`'s `mat_cursor` and `pg2iceberg.log-end` are ahead of the restored catalog pointer, and define the exact re-registration or replay procedure without double-applying TOAST updates.
   - Measure and record RPO (committed snapshots lost or needing reconciliation), RTO (time to healthy catalog + active readers + resumed writer), and post-restore exact row diff (`lab/compare.py`) plus OpenFGA permission check (`lab/l2.py`).

### Operations owner list required before self-hosting

| Surface | Responsibilities to assign to a named owner |
| --- | --- |
| **Catalog Postgres (`lakekeeper-db`, `openfga-db`)** | Provisioning, HA/failover, PITR backups, restore drills, Postgres major/minor upgrades, connection pooling, disk/bloat alerts, and custody of `LAKEKEEPER__PG_ENCRYPTION_KEY`. |
| **Object storage (S3 / Silo / ADLS)** | Bucket lifecycle, encryption, IAM/STS role policies, prefix isolation for warehouses/tables, availability SLAs, and storage growth budgets. |
| **Credentials and identity (Keycloak / OIDC / OpenFGA / STS)** | IdP availability, client secret rotation, OIDC signing key rollover, OpenFGA store/model upgrades, least-privilege grant review, and break-glass admin access. |
| **Monitoring and supervision** | Process supervision (`restart: on-failure` / Kubernetes Deployment with crash-loop alerting) for `pg2iceberg` and `lakekeeper`; alerts on `pg_replication_slots` `active=false` and `wal_gap_bytes_restart` (to prevent source PG disk exhaustion during prolonged catalog outages); alerts on `log_seq - mat_cursor` backlog, `pg2iceberg` `/healthz` & `/readyz`, and Lakekeeper HTTP 5xx/latency. |
| **Iceberg file maintenance** | Scheduled compaction (`target_file_size` / `pg2iceberg compact`) to bound equality-delete read amplification, snapshot expiration (`pg2iceberg maintain`), staged log-file pruning (`_pg2iceberg.log_index` + S3 staging prefix), and orphan-file cleanup (removing uncommitted Parquet files left behind by catalog outages as observed in this drill). |

## Limitations

- Tested with a single `60 s` outage at `10.0 ops/s` (`~1.77 MB` WAL retained). Multi-hour outages where PostgreSQL `max_slot_wal_keep_size` could invalidate `pg2iceberg_slot` (forcing a full re-snapshot) or where cached vended STS tokens expire (`3600 s` default) were not exercised.
- Distributed mode (`pg2iceberg stream-only` + `pg2iceberg materializer-only`), where `run.rs:478-484` catches materializer cycle failures without stopping the flusher, was not tested in this milestone.
- No metadata backup/restore was executed (per the plan).
