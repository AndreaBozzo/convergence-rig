# Milestone L2 Report: Scoped Access with Distinct Identities

**Verdict:** `pass` (outcome: `converged`)

Lakekeeper `0.15.1` ran under Compose profile `authz` with OpenFGA `v1.14` (`authz-backend=openfga`) and Keycloak `26.0.7` OIDC (`realm=cdclab`). Three distinct service-account identities (`cdclab-admin`, `cdclab-writer`, `cdclab-reader`) were verified. The writer created `raw.orders` and `curated.orders` in disjoint S3 prefixes under `s3://cdclab/authz-warehouse/`, and the reader received table-level `select` on `curated.orders` only. All four required checks passed with positive and negative controls: (1) the reader loaded `curated.orders` (HTTP `200`), scanned its rows in DuckDB, and fetched its Parquet file via vended STS credentials (HTTP `200`, valid `PAR1`); (2) the catalog denied `raw.orders` to the reader (REST HTTP `404 NoSuchTableException`, DuckDB `CatalogException`), while serving HTTP `200` to the writer; (3) the reader's `curated`-scoped vended STS credentials were denied by Silo on both `raw.orders` Parquet files (HTTP `403 AccessDenied`), while the writer's `raw`-scoped vended credentials fetched the same file (HTTP `200`, valid `PAR1`); and (4) the writer appended new rows to both `raw.orders` and `curated.orders` after reader grants were active, while the reader's commit attempt on `curated.orders` failed with HTTP `403 TableActionForbidden`. Project-only cleanup removed all `cdclab` containers, volumes and networks and left all `14` unrelated host containers unchanged.

Raw evidence is committed under [runs/20261119T210151Z-l2-authz-scoped-access/](../runs/20261119T210151Z-l2-authz-scoped-access/).

## Scope boundary of object-level authorization

Lakekeeper with OpenFGA and vended storage credentials authorizes at the **object level** (server, project, warehouse, namespace, table, view) and downscopes storage credentials to the allowed table's prefix. It does **not** enforce **row-level filters** or **column-level masks** inside a table: any principal granted `select` on a table receives storage credentials that can read the entire Parquet data files of that table. Enforcing row filters or column masks requires either a policy-enforcing query engine sitting in front of storage or materializing a separate curated table (as demonstrated by separating `raw.orders` with `pii_note` from `curated.orders` with `tier`).

## Limitations

- Tested locally against Silo (`s3-compat` STS session policies). Cloud storage backends (AWS S3 IAM roles, ADLS Gen2 SAS/RBAC, GCS) have different credential-vending mechanisms and policy limits; ADLS is out of scope for this local lab and would need a separate verification if ADLS is the target storage.
- Writer writes in L2 were performed by Spark (`cdclab-writer` via OAuth2 `client_credentials`), not `pg2iceberg`. As verified in `pg2iceberg` `v0.12.0` (`crates/pg2iceberg/src/config.rs`), `pg2iceberg`'s `catalog_auth: oauth2` defaults `oauth2-server-uri` to `{catalog_uri}/v1/oauth/tokens` unless overridden via `catalog_props` (`oauth2-server-uri` and `scope`), which was not exercised in this run.
- Keycloak ran in `start-dev` mode over plain HTTP on `127.0.0.1` with synthetic lab secrets.
