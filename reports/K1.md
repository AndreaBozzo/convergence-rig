# Milestone K1 Report: Orphan Files After a Catalog Outage

**Verdict:** `pass` (outcome: `converged`; Lakekeeper OSS `v0.15.1` has no orphan-file removal; Apache Spark `3.5.9` + Iceberg `1.12.0` removed exactly the `2` unreferenced outage Parquet files while preserving all `87` referenced Iceberg objects and all `63` `pg2iceberg` staging objects; post-cleanup exact diff matched `25,039 = 25,039` rows; concurrent default-retention `remove_orphan_files` during active writes and snapshot `seq=19` commit removed `0` live or staging files and post-concurrent diff matched `25,063 = 25,063` rows)

Reproducing the L3 `60 s` Lakekeeper catalog outage with connector restart on the `25,000`-row fixture left `152` objects (`15,135,177 B`) under the Iceberg table prefix: `87` referenced Iceberg metadata/data/delete objects, `63` `pg2iceberg` staging files under `staged/`, and `2` unreferenced orphan Parquet files (`358,700 B`) uploaded right before `pg2iceberg 0.12.0` exited. Probing the pinned `quay.io/lakekeeper/catalog:v0.15.1` management API and OpenAPI spec confirmed that Lakekeeper OSS has no `remove_orphan_files`, `expire_snapshots`, or `optimize` task queues (all return HTTP `404 QueueNotFound`); it ships only `soft_deletion`, `tabular_purge`, `task_log_cleanup`, and commit-time `.metadata.json` log pruning. Using the L1 Spark image (`cdclab/spark-iceberg:3.5.9-iceberg1.12.0`) with Lakekeeper vended STS credentials revealed two operational requirements: (1) `pg2iceberg 0.12.0` stores its staged WAL Parquet files inside the table's own prefix (`<table_location>/staged/`), so an unscoped table-root dry run flagged all `63` staging files alongside the `2` orphans (`65` total) and cleanup must be scoped to `location => '<table_location>/data'` with `prefix_listing => true`; and (2) Iceberg `1.12.0`'s SQL procedure `CALL cdclab.system.remove_orphan_files` rejects any `older_than` interval shorter than 24 hours (`IllegalArgumentException`), requiring `SparkActions.deleteOrphanFiles` for immediate quiescent cleanup after an outage. Scoped cleanup removed exactly the `2` unreferenced files (`0` referenced removed, `0` staging removed, `0` unreferenced remaining), and DuckDB exact verification passed (`25,039 = 25,039`, `0/0/0/0` diffs). Running the standard SQL procedure `CALL cdclab.system.remove_orphan_files(table => 'public.orders', location => '<table_location>/data', prefix_listing => true)` with default 3-day retention while `pg2iceberg` actively wrote `58` PG commits and committed snapshot `seq=19` mid-call removed `0` files, and post-concurrent exact verification passed (`25,063 = 25,063`, `0/0/0/0` diffs). Project-only cleanup left `0` `cdclab` resources and all `14` unrelated host containers unchanged.

## Limitations

- Immediate cleanup of <24-hour-old outage orphans required Iceberg's Java `SparkActions.deleteOrphanFiles` API (`olderThan` set `~13 s` before execution on a quiescent table); in production, operators normally wait past the 3-day default retention window so the standard SQL procedure `CALL catalog.system.remove_orphan_files` runs safely without stopping writers.
- Only orphans under `data/` were created by the L3 outage; uncommitted `metadata/` files (for example from a catalog failure after uploading an Avro manifest or `.metadata.json` file) were not observed in `pg2iceberg 0.12.0` and would require an additional `location => '<table_location>/metadata'` pass if they occurred.
- `pg2iceberg 0.12.0` retained all `63` (then `89`) `staged/*.parquet` files under `<table_location>/staged/` across the entire run; staging-file retention/pruning by `pg2iceberg` over multi-day runs was not tested here.

## Open questions and gaps noticed

- **Capability/ops gap (`pg2iceberg 0.12.0` staging layout):** Placing `pg2iceberg`'s `staged/*.parquet` objects inside the Iceberg table root `<table_location>/staged/` collides with standard Iceberg table-root `remove_orphan_files` maintenance once staged files age beyond `older_than`. Separating staging into a sibling prefix (or documenting `location => '<table_location>/data'` alongside `pg2iceberg` staging cleanup) avoids accidental deletion of active or replayable staging files.
- **Lakekeeper OSS vs Lakekeeper Plus boundary:** Self-hosting OSS Lakekeeper `v0.15.1` means table maintenance (`remove_orphan_files`, `expire_snapshots`, compaction) must be scheduled externally (e.g. Spark CronJob for orphan removal plus `pg2iceberg compact`/`maintain`), whereas Lakekeeper OSS manages only catalog metadata, soft-deletion grace periods, and dropped-table purges.
- **Next milestone (K2):** Test what happens to CDC convergence and `_pg2iceberg` coordinator alignment when `lakekeeper-db` is restored from an earlier `pg_dump` backup while `pg2iceberg` is running.
