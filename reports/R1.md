# Milestone R1 Report: Minimal Upstream Reproduction of the Catalog-Outage Exit

**Verdict:** `pass` (`3/3` clean single-process runs reproduced the fatal exit with identical `RESULT:` lines and exit code `1`; split-mode comparison survived the same outage with exit code `0` and advanced the Iceberg snapshot on recovery)

A standalone, lab-free reproduction package is committed under [repro/pg2iceberg-catalog-outage/](../repro/pg2iceberg-catalog-outage/) (`docker-compose.yml`, `pg2iceberg.yaml`, `repro.sh`, `README.md`). It uses only public multi-arch container images pinned by digest, Compose project `p2irepro`, ports bound to `127.0.0.1` and disjoint from `cdclab`, and POSIX `/bin/sh` with `docker compose`, `docker inspect`, `psql` inside `pg-source`, and `curl` (no Python, no lab modules). In three consecutive clean runs from Git Bash on Windows 11, `polynyadev/pg2iceberg:0.12.0` in single-process `run` mode replicated the initial 5-row snapshot on PostgreSQL 17, then exited with code `1` roughly `13.8-13.9 s` after Lakekeeper stopped, leaving `pg2iceberg_slot` inactive (`active=false`) and the Iceberg snapshot frozen after Lakekeeper returned. Running the same steps in split mode (`repro.sh split`: `stream-only` plus `materializer-only --worker-id worker-1` on the same `pg2iceberg.yaml`) kept both processes running across the outage, kept `pg2iceberg_slot` active, logged retry warnings during the outage, and committed a new snapshot once Lakekeeper came back. Project-only cleanup (`repro.sh down`) removed all `p2irepro` containers, volumes and networks while leaving all `14` unrelated host containers unchanged.

Raw evidence for the three single-process runs, the split-mode run, and final cleanup is committed under [runs/20261119T232348Z-r1-catalog-outage-repro/](../runs/20261119T232348Z-r1-catalog-outage-repro/). The local upstream issue draft [drafts/pg2iceberg-catalog-outage-exit.md](../drafts/pg2iceberg-catalog-outage-exit.md) now points at `repro/pg2iceberg-catalog-outage/` with the exact `RESULT:` output.

### 3. Failed trial summary (harness fix kept on record)

During initial development of `repro.sh split`, starting `pg2iceberg-stream` and `pg2iceberg-materializer` simultaneously against an empty Lakekeeper catalog caused `pg2iceberg-materializer` to exit immediately with code `1` (`Error: register public.items` / `catalog: conflict: TableAlreadyExists => The table already exists`) because both processes raced to create `public.items`. `repro.sh split` was updated to start `pg2iceberg-stream` until the initial snapshot exists in Lakekeeper before starting `pg2iceberg-materializer`, after which split mode ran cleanly end to end.

## Git Bash (Windows 11) vs Linux and macOS notes

- **Line endings and permissions:** `repro.sh` is stored with LF line endings (`.gitattributes` enforces `*.sh text eol=lf`) and executable mode in Git so Linux and macOS users can run `./repro.sh` directly.
- **Carriage returns from `docker.exe` on Windows:** Under Git Bash on Windows, native `docker.exe` and `psql` output through Docker can emit trailing `\r` characters; `repro.sh` strips `\r` with `tr -d '\r'` where values are captured into variables. On Linux and macOS this is a harmless no-op.
- **MSYS2 path conversion:** `repro.sh` changes directory into its own folder (`cd "$SCRIPT_DIR"`) and passes relative `-f docker-compose.yml` and avoids standalone leading-`/` arguments to `docker.exe`, so it runs in Git Bash without requiring `MSYS_NO_PATHCONV=1`.
- **PowerShell stderr wrapping in captured logs:** Because the four verification runs were launched from Windows PowerShell 5.1 invoking Git Bash (`& 'C:\Program Files\Git\bin\bash.exe' ... *> ...`), the first `docker compose` stderr progress line in each `.log` file carries a PowerShell `NativeCommandError` header (and PowerShell initially wrote UTF-16LE, which was converted losslessly to UTF-8 LF for Git readability). Running `./repro.sh` directly inside a Linux, macOS, or interactive Git Bash terminal does not add that wrapper.
- **BSD `sed` (macOS) vs GNU `sed` (Linux/Git Bash):** `repro.sh` uses POSIX BRE patterns (`[[:space:]]`, `[0-9][0-9]*`) and always appends a trailing newline (`printf '%s\n'`) before piping into `sed` so macOS BSD `sed` matches identically to GNU `sed`.

## Limitations

- Tested on Windows 11 (`AMD64`) with Docker Desktop `4.99.0` and Git Bash; not directly executed on a physical Linux or macOS (`arm64`) host in this session, though all images are pinned by multi-arch manifest index digests and `repro.sh` uses POSIX `/bin/sh` constructs verified with `sh -n`.
- `repro.sh` checks container exit status, replication slot activity, and Iceberg `current-snapshot-id` presence/advancement via `curl`; it does not attach DuckDB or diff row contents (full row-level verification during catalog outage recovery was already established in [reports/L3.md](L3.md)).
