# Milestone W1 Report: Start CDC with `wal_level=replica`

**Verdict:** `pass` (outcome: `accepted and converged`). On a fresh PostgreSQL `19.0` source with `wal_level=replica` and zero logical slots, `pg2iceberg 0.12.0` started, created its own slot, took the initial snapshot and replicated a `60 s` workload. The exact comparison matched (`2,520 = 2,520`, `0/0/0/0` diffs, `schema_id=0`). PostgreSQL raised `effective_wal_level` from `replica` to `logical` when the slot was created. `pg2iceberg run` has no `wal_level` preflight, so nothing refused. Only `pg2iceberg init` checks it, and its check is wrong for PostgreSQL 19: it printed a failing line (`wal_level is replica`) before the slot existed and again while the connector was running. A local upstream draft is in [drafts/pg2iceberg-init-wal-level-preflight.md](../drafts/pg2iceberg-init-wal-level-preflight.md).

Raw evidence: [runs/20261120T134349Z-w1-wal-level-replica/](../runs/20261120T134349Z-w1-wal-level-replica/) (`summary.json` has every number below).

## Settings before and after the first logical slot

All reads are `SHOW` plus `pg_settings` on the source. `wal_level` has context `postmaster` and `effective_wal_level` has context `internal` (read-only). The server was started with `-c wal_level=replica` through `PG_SOURCE_WAL_LEVEL=replica` (new in [compose/docker-compose.yml](../compose/docker-compose.yml), default still `logical`).

`wal_level` never changed. Native slot creation took `440.12 ms` on this host. After each drop the first read already showed `replica` (`elapsed_ms: 0.0`, no `CHECKPOINT` needed). PostgreSQL's documentation says the switch back is performed asynchronously by the checkpointer, so a slower fall-back on a busy server is possible; this run did not see one. The first row of the table and the last two rows establish the PostgreSQL side: logical decoding turned on at the first slot and off at the last drop, as the [PostgreSQL 19 logical decoding page](https://www.postgresql.org/docs/19/logicaldecoding-explanation.html) describes ("When `wal_level` is set to `replica`, logical decoding is automatically activated upon creation of the first logical replication slot").

## What pg2iceberg 0.12.0 does

Pinned source: tag `v0.12.0`, commit `01c2e172eb5e7be82c60b77f20cb089354c06ce6`, checked out in `upstream/pg2iceberg-v0.12.0/` (the run records `git rev-parse HEAD` and the quoted lines in [pg2iceberg_source_quotes.json](../runs/20261120T134349Z-w1-wal-level-replica/pg2iceberg_source_quotes.json); every quote carries a `found_expected_text` flag, all `true`).

**The only `wal_level` check is in `pg2iceberg init`.** `crates/pg2iceberg/src/init.rs:97-107`:

```rust
let wal_level: String = one("SHOW wal_level".into()).await?.get(0);
checks.push(Check {
    what: format!("wal_level is {wal_level}"),
    fix: (wal_level != "logical").then(|| {
        "set wal_level = logical and restart Postgres (RDS / Aurora: \
         rds.logical_replication = 1 in the parameter group; Cloud SQL: the \
         cloudsql.logical_decoding flag)"
            .into()
    }),
});
```

`init` only reports. `report()` in the same file (`init.rs:339`, `:359`) prints `✗ {what} — {fix}` and the line `fix what's marked ✗ before starting pg2iceberg`; the command still exits `0` and writes its config. A grep for `wal_level` over the whole tree finds only this check, one error message about the removed `source.mode: query` (`config.rs:947`), integration-test settings and documentation lines.

**`run` creates the slot without checking.** `crates/pg2iceberg-validate/src/runtime.rs:531-545` calls `lc.pg.create_slot(&lc.slot_name)` when the slot is fresh, which issues `CREATE_REPLICATION_SLOT <slot> LOGICAL pgoutput NOEXPORT_SNAPSHOT` (`crates/pg2iceberg-pg/src/prod/client.rs:305-314`). PostgreSQL 19 accepts that command at `wal_level=replica`. `connect-pg` also passes (`OK: PG replication-mode connection established`, `slot does not exist; would be created on first run`).

Observed with the pinned image `polynyadev/pg2iceberg:0.12.0@sha256:4d76b19dedfdb36adf6b01978bb1c9460d178ab83603fe9c7efadd01b61d3b6b`:

| Command | When | Result |
| --- | --- | --- |
| `pg2iceberg init --output -` | no slot, `effective_wal_level=replica` | exit `0`; `✗ wal_level is replica — set wal_level = logical and restart Postgres ...`; other four checks `✓` ([stderr](../runs/20261120T134349Z-w1-wal-level-replica/init_before_slot.stderr.txt)) |
| `pg2iceberg connect-pg` | no slot | exit `0`, `OK` ([output](../runs/20261120T134349Z-w1-wal-level-replica/connect_pg_before_slot.txt)) |
| `pg2iceberg run` | no slot | not refused; log line `replication slot created` (`cp: Lsn(30982672)`), `snapshot phase complete` about `1.0 s` later |
| `pg2iceberg init --output -` | connector running, `effective_wal_level=logical` | exit `0`; same `✗ wal_level is replica` line ([stderr](../runs/20261120T134349Z-w1-wal-level-replica/init_after_slot.stderr.txt)) |

So the question the plan names, whether a preflight that requires logical before the first slot exists blocks the clean-start case, has this answer for `0.12.0`: the `init` preflight does flag it, but it is advisory and `run` is not blocked. The documentation does state `wal_level = logical` as a requirement (`docs/getting-started/installation.md:57`, `docs/getting-started/quickstart.md:25`, `docs/usage/configuration.md:81`), so an operator who follows `init`'s advice restarts the server needlessly on PostgreSQL 19.

## Tests

`tests/test_w1_unit.py` covers the stderr parser, the outcome classifier and the log counter. The classifier is checked on its fault inputs: a start that is not clean (an existing logical slot, or `wal_level=logical`) gives `invalid harness run`, a connector that never started gives `refused`, a failed comparison gives `accepted, mismatch at deadline`, and the contradiction flag is true only when the preflight fails while `effective_wal_level` is `logical`. The run itself guards the starting state: `classify_w1` returns `invalid harness run` unless `wal_level`, `effective_wal_level` and the logical slot count are `replica`, `replica` and `0` immediately before the connector starts.

## Limitations

- One run, one table, `2,500` rows, `60 s`. The result is about acceptance and convergence, not about timing.
- Only PostgreSQL `19.0` was tested. Behaviour of `CREATE_REPLICATION_SLOT` at `wal_level=replica` on earlier servers was not tested, so the draft makes no claim about them.
- The restart row shows that a kept slot brings `effective_wal_level` back to `logical` after a server restart. The connector was not restarted afterwards, so resumption from that state is not evidenced here.
- Standbys are not covered. The PostgreSQL page warns that dropping or invalidating the last logical slot at `wal_level=replica` invalidates slots on standbys.
- The `init` finding is advisory only: it does not stop `run`.

## Gaps noticed

- `pg2iceberg init` could read `effective_wal_level` (draft above).
- A test that restarts the connector after the source restart in row 5 would show resumption at `wal_level=replica`.

## Upstream openings

`pg2iceberg init`: treat `wal_level=replica` as acceptable on PostgreSQL 19 and later by reading `effective_wal_level` or by softening the message. Draft only, not submitted.
