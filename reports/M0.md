# Milestone M0 Report: Prove the Reader Path

**Verdict:** `pass` (outcome: `converged`)

The PostgreSQL 19.0 -> pg2iceberg 0.12.0 -> Lakekeeper 0.15.1 -> Silo -> DuckDB 2.0.0 stack started from a fresh state, passed repeated idempotent bootstrap, replicated an insert, update and delete on `public.orders`, and served exact results through DuckDB while the tested Iceberg snapshot still referenced a live equality-delete file. Snapshot-pinned reads returned both the post-mutation snapshot and the historical post-insert snapshot accurately. Project-only cleanup removed all `cdclab` containers, volumes and networks without touching unrelated containers on the host.

Raw evidence for this run is committed under [runs/20261119T182830Z-m0/](../runs/20261119T182830Z-m0/).

## Commands run

From the repository root (`C:\dev\cdc-convergence-lab`):

1. Build the pinned PostgreSQL 19.0 image from the official release tarball:
   ```text
   docker compose -p cdclab --env-file compose/.env -f compose/docker-compose.yml build pg-source
   ```
2. Pull the pinned service images:
   ```text
   docker compose -p cdclab --env-file compose/.env -f compose/docker-compose.yml --profile connector pull lakekeeper-db silo lakekeeper pg2iceberg
   ```
3. Run the end-to-end M0 harness:
   ```text
   uv run python -m lab.m0
   ```
   Internally, `lab.m0` executed these exact Compose invocations (recorded in [runs/20261119T182830Z-m0/summary.json](../runs/20261119T182830Z-m0/summary.json)):
   ```text
   docker compose -p cdclab --env-file compose/.env -f compose/docker-compose.yml --profile connector down -v --remove-orphans
   docker compose -p cdclab --env-file compose/.env -f compose/docker-compose.yml up -d --wait
   docker compose -p cdclab --env-file compose/.env -f compose/docker-compose.yml --profile connector up -d pg2iceberg
   docker compose -p cdclab --env-file compose/.env -f compose/docker-compose.yml --profile connector down -v --remove-orphans
   ```
4. Run unit tests:
   ```text
   uv run pytest -q
   ```

## Limitations

- `postgres:19.0` was not yet published on Docker Hub on 2026-11-19 (the day of PostgreSQL 19.0 GA), so `pg-source` is built locally from the official `postgresql-19.0.tar.bz2` release tarball with verified SHA-256. Once the official `postgres:19.0` image lands, the lab can switch to its pinned digest if desired, or keep the tarball build for reproducibility across M1-M3.
- Automatic compaction in `pg2iceberg` was disabled (`target_file_size: 0`) for M0 so the 2-row update/delete test would keep equality-delete files uncompacted on the tested snapshot. M1-M3 should decide explicitly whether compaction stays off or uses tuned thresholds.
- Storage backend is Silo (`pgsty/silo:RELEASE.2026-09-03T13-18-01Z`), matching Lakekeeper `v0.15.1`'s minimal quickstart, rather than SeaweedFS.
- DuckDB Python `fetchall()` on `TIMESTAMPTZ` columns requires `pytz` to be installed in the `uv` environment.
- In `lab/m0.py`, `str(Decimal("0.000000001"))` serialized small decimals in scientific notation (`1E-9`) in JSON output; M1's comparison module should format decimals in canonical fixed-point (`format(d, "f")`) and compare `Decimal` values directly under a 38-digit context.

## Open questions

- For M1-M3, should `pg2iceberg` keep `target_file_size: 0` (no background compaction during measured runs, exercising DuckDB equality-delete reads at scale) or enable compaction with explicit thresholds?
- Should M1 keep the tarball-built `cdclab/postgres:19.0` image for consistency across M0-M3, even if `postgres:19.0` appears on Docker Hub before M1 runs?
- If M2 uncovers any discrepancy between PostgreSQL and DuckDB on a REPACK snapshot, Spark with Iceberg will be needed on demand as the independent second reader per the plan.
