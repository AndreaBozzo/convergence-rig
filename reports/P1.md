## Decision: Does Lakekeeper earn its place against Apache Polaris?

Both catalogs pass the exact same CDC convergence, multi-engine equality-delete readback, and prefix-scoped STS isolation checks. Neither wins on Iceberg correctness or reader compatibility. The choice comes down to operational architecture:

- **Apache Polaris `1.9.0` fits better when you want a self-contained authenticated catalog** with minimal moving parts. One 3-service stack (`polaris-db`, `polaris-bootstrap`, `polaris`, `69` config lines) provides both catalog metadata and OAuth2 + RBAC, starts in `13.4 s`, and idles at `368.0 MiB` combined RAM (vs `28.5 s`, `886.4 MiB`, `7` services, and `358` config lines for Lakekeeper + OpenFGA + self-hosted Keycloak). Polaris also speaks Iceberg REST OAuth2 directly at `/api/catalog/v1/oauth/tokens`, matching `pg2iceberg 0.12.0`'s default `catalog_auth: oauth2` flow without custom token-endpoint overrides.
- **Lakekeeper `v0.15.1` earns its place when you want minimal catalog footprint, cleaner S3-compatible storage setup, or ReBAC/soft-delete features.** As a compiled Rust binary, Lakekeeper idles at `35.3 MiB` (`37.1 MiB` with OpenFGA) vs Polaris's JVM footprint of `333.4 MiB` idle and `425.4 MiB` under the M1 workload (and Quarkus defaults its Caffeine cache cap to `~6720 MB` under `-XX:MaxRAMPercentage=80.0` unless container memory limits are set). If an enterprise OIDC provider (such as Entra ID or Okta) already exists so Keycloak is not self-hosted, Lakekeeper + OpenFGA + both Postgres DBs total `179.9 MiB` idle RAM. Lakekeeper also worked with Silo STS without KMS/roleArn workarounds, hides unauthorized table/namespace existence with `404 NoSuchTableException`, allows direct user-to-object grants without a 4-tier role chain, and ships built-in `soft_deletion` and `tabular_purge` task queues.

#### Access-control mapping: Polaris RBAC vs Lakekeeper OpenFGA

| Concept | Lakekeeper `v0.15.1` + OpenFGA `v1.14` | Apache Polaris `1.9.0` | Mapping note |
| --- | --- | --- | --- |
| Identity source | External OIDC (Keycloak) | Built-in OAuth2 principals (external OIDC optional) | Polaris removes Keycloak for local/service-principal setups. |
| Authorization model | ReBAC graph (OpenFGA); direct user/role assignments | 4-tier RBAC (`Principal -> PrincipalRole -> CatalogRole -> Grant`) | Polaris requires creating and binding two role layers plus requesting `PRINCIPAL_ROLE:<name>` in OAuth2 scope. |
| Writer grant | `create` + `modify` on warehouse | `CATALOG_MANAGE_CONTENT` on catalog role | Maps cleanly; both allow creating namespaces/tables and writing data. |
| Read-only table grant | `select` on table UUID | `TABLE_READ_DATA` on `["curated"]` / `orders` | Maps cleanly; both trigger read-only prefix-scoped STS credential vending. |
| Unauthorized table response | `404 NoSuchTableException` (hides existence) | `403 ForbiddenException` (names principal, active roles, and denied op) | Does not map identically; Polaris leaks authorization diagnostics rather than hiding existence. |
| `/v1/config` gating | Gated by OIDC + warehouse permissions | Ungated by default (`ENFORCE_CATALOG_CONFIG_AUTHORIZATION=false`, logged as production warning) | Enabling it in production requires granting `CATALOG_READ_CONFIG` explicitly. |
| Row filters & column masks | Not supported (object-level only) | Not supported (object-level only) | Same boundary in both catalogs; requires a query engine or curated table. |

### 4. Workaround discovered during initial Silo STS probe (kept on record)

During the initial live probe of Polaris `1.9.0` against Silo before running the official checks, creating `cdclab_polaris` with `stsUnavailable: false` and default `kmsUnavailable` (`false`) succeeded (`HTTP 201`) and created a probe table (`HTTP 200`), but `LoadTable` with `X-Iceberg-Access-Delegation: vended-credentials` failed with `HTTP 400 StsException`:

```json
{"error":{"message":"invalid resource 'arn:aws:kms:local-01:000000000000:key/*' (Service: Sts, Status Code: 400, ...)","type":"StsException","code":400}}
```

Polaris `1.9.0` emits a wildcard KMS statement (`arn:aws:kms:<region>:<account>:key/*`) in its STS inline session policy unless `"kmsUnavailable": true` is explicitly set in `storageConfigInfo` (documented in Apache Polaris storage configuration / issue #3440). Setting `"kmsUnavailable": true` alongside `"stsUnavailable": false` and `SYNTHETIC_SILO_ROLE_ARN` (`arn:aws:iam::000000000000:role/cdclab-polaris`) resolved the error immediately and enabled full downscoped STS credential vending on Silo.

## Limitations

- Lakekeeper's M1/L1/L2 results were taken verbatim from committed runs (`2026-11-19`) and not re-run (per plan). Because host Docker Desktop fsync latency was faster on `2026-11-20` (`4.98 ms` PG exec p50 in P1 vs `14.56 ms` in M1) and Lakekeeper M1 did not record `docker stats`, under-workload memory is reported only for Polaris, and cross-session latency deltas (such as DuckDB diff time `1.29 s` vs `2.90 s`) reflect host session variance rather than catalog speed.
- Polaris ran with its built-in OAuth2 token broker and auto-generated RSA keypair (producing 4 production-readiness startup warnings in `polaris.log`: ephemeral RSA keys, optional `Polaris-Realm` header, and `ENFORCE_CATALOG_CONFIG_AUTHORIZATION=false`). Production deployments require persistent RSA keys or external OIDC plus enabling `ENFORCE_CATALOG_CONFIG_AUTHORIZATION`.
- Concurrent REPACK (M2/M3), catalog outage (L3), orphan cleanup (K1), and catalog DB restore (K2) were not repeated on Polaris (out of scope for P1).

## Open questions and gaps noticed

- **JVM memory sizing in Polaris `1.9.0`:** With default container settings (`-XX:MaxRAMPercentage=80.0`), Polaris initialized its Caffeine persistence cache to `~6720 MB` on this `15.38 GiB` Docker Desktop VM. Production deployments should set explicit container memory limits or Quarkus JVM heap bounds so cache growth cannot OOM-kill the catalog container.
- **Polaris S3-compatible STS ergonomics:** Requiring both `"kmsUnavailable": true` and a dummy `roleArn` for non-AWS STS backends (MinIO/Silo) is non-obvious compared to Lakekeeper's `flavor: s3-compat` profile.
- **Polaris policy / maintenance APIs:** Polaris `1.9.0`'s `/v1/config` advertised `/polaris/v1/.../policies` and `/api/openlineage/v1/lineage` endpoints; whether Polaris's policy attachments can coordinate Iceberg table maintenance (such as orphan cleanup or snapshot expiration) was not tested in P1.
