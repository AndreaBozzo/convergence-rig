# Milestone D1 Report: Databricks Free Edition through Unity Catalog's Iceberg REST endpoint

**Verdict:** `partial` (the feasibility questions are answered and one table is left for the demo; the exact CDC comparison through the endpoint is blocked, in two independent places). In this workspace Unity Catalog's Iceberg REST endpoint serves metadata, table creation and vended credentials, but the vended credentials cannot read or write the table's S3 files (explicit deny in a bucket policy), and `pg2iceberg 0.12.0` cannot create its table because Unity Catalog refuses identifier columns. Neither DuckDB nor Spark could read table data through the endpoint, so no exact comparison through the endpoint exists. The demo table `orders_demo` (`1,000` rows, same seven columns as the lab fixture) was written and checked row by row inside Databricks instead.

## The plan's read-only fallback, and what was done instead

The plan's fallback is a small managed table created in Databricks and read exactly by DuckDB and Spark through the endpoint. The table exists, but both external reads fail at S3 (above), so that comparison could not be made. What was verified instead:

1. `orders_demo` was created over REST by Spark (the empty table, `Created By: Spark`, `Type: MANAGED`, `Provider: iceberg`).
2. Databricks SQL wrote `1,000` rows (`id <= 1000` of the seeded `public.orders`, including the `12` edge-case rows and the `50` TOAST rows) with `20` `INSERT ... SELECT ... FROM VALUES` statements. Text travels hex-encoded and decimals as text, so quoting and newlines cannot change a value. All `20` statements succeeded; `1,000` rows, `20` snapshots in the REST metadata.
3. A per-row fingerprint was computed twice and compared by `id`: in Databricks, `md5(concat_ws('|', id, status, CAST(amount AS STRING), unix_micros(updated_at), coalesce(note,'<null>'), coalesce(payload,'<null>'), coalesce(CAST(discount AS STRING),'<null>')))`; and in Python from a repeatable-read PostgreSQL query with the same canonical text (`lab.d1.row_hash_text`). Result: `1,000` expected, `1,000` actual, `0` missing, `0` extra, `0` duplicate, `0` differing ids. NULL and empty text are distinguished by the `<null>` marker; decimals compare as exact text (`0.000000000` and the 29-digit edge values included); timestamps compare as microseconds since the epoch.
4. The table's REST metadata passed the lab's schema check (`lab.compare.verify_iceberg_schema`, no identifier fields expected): types `long`, `string`, `decimal(38, 9)`, `timestamptz`, required flags as in the fixture.

Limits of this check: it is an md5 fingerprint per row computed by Databricks, not DuckDB's or Spark's own decoding of the Parquet files, so it shows that the stored rows equal the source, not that an external engine can read them. JSON payload text is compared as text (it comes from `payload::text`), not structurally.

## Credential handling

The token is read from `compose/.env.local` inside `lab.d1` and sent only as an HTTPS bearer header (and to DuckDB through a `CREATE SECRET`). Every file the module writes goes through `Redactor`, which replaces the token, the workspace host, the token's own shape, AWS key ids and session tokens, role ARNs, the managed-storage bucket and metastore ids, and the `x-databricks-org-id` header. The REST config blocks keep key names and the expiry only. Before the commit I scanned every new and modified file for the token value, its prefix, the host, the AWS key shapes and the account identifiers (`0` hits; the scan is `scan_for_secrets` plus a needle list). Temporary credentials were printed once in my own terminal during exploratory requests and are not in any file; they had a one-hour lifetime.

## Tests

`tests/test_d1_unit.py` (`16` tests) covers redaction of every credential shape, the pre-commit scan, credential stripping, the pg2iceberg failure classifier (catalog refusal, orphan refusal, running, exited, unknown), cleanup planning, the row-fingerprint comparison, the S3 denial classifier and the SQL `INSERT` builder. The comparison and the classifiers are checked on faulty inputs: a missing id, an extra id, a duplicated id and a changed hash each fail the fingerprint comparison; a token left in unredacted text is flagged by the scan and absent after redaction; a log line that mentions the snapshot but exited with an error does not classify as running.

## Limitations

- Storage format of `orders_demo`: `DESCRIBE TABLE EXTENDED` reports `Provider: iceberg`, while the Unity Catalog tables API reports `data_source_format: DELTA` with `delta.universalFormat.enabledFormats = iceberg` and `delta.enableIcebergCompatV2 = true`. On this workspace the managed table is stored as Delta with Iceberg metadata (UniForm). Whether that bears on the vended-credential deny was not tested.
- One workspace, one run of the final module, Free Edition. The explicit S3 deny may be specific to this edition or to this storage; it was not tested elsewhere.
- No external engine read any data file, so DuckDB and Spark equality-delete handling on Unity Catalog tables is untested here.
- The `orders_demo` check is a fingerprint comparison made inside Databricks (see above).
- The plan's 60 s pg2iceberg workload on the 2,500-row fixture did not run.
- The token is a two-day token; this report cannot be rerun after it expires.

## Gaps noticed

- `pg2iceberg` always declares its primary key as identifier fields at table creation; a catalog that refuses them (Unity Catalog here) cannot be a sink. A table-creation option without identifier fields would help only if the writer's equality deletes can work without them, which was not examined.
- `pg2iceberg` has no documented way to adopt an existing table for a fresh install; the `OrphanedTables` check requires deleting it first.
- The lab has no external-reader check that separates a catalog refusal from a storage refusal; here the two were told apart by the AWS error text.
- A Databricks-side reader that fingerprints `orders_demo` could be rerun after any token renewal to confirm the demo table is intact.
