# Milestone M2 Report: Run Concurrent REPACK

**Verdict:** `pass` (baseline outcome: `converged`; concurrent REPACK outcome: `converged`; overlap confirmed: `45` writes committed during a `4,499.43 ms` REPACK window)

PostgreSQL 19.0 executed `REPACK (CONCURRENTLY) public.orders` on a 250,000-row table (`467.3 MB` including `25,000` out-of-line TOAST rows) while the paced `10.0 ops/s` workload committed `45` concurrent writes (`15` normal updates, `8` unchanged-TOAST updates, `10` changed-TOAST updates, `6` inserts, `6` deletes) during the rewrite. Both the fresh baseline run and the fresh concurrent-REPACK run completed all `1,800` scheduled operations with zero errors, zero timeouts, and zero missed arrivals, and both converged on their first marker-bearing Iceberg snapshots (`4016379093415438975` and `8007425982733359985`) with an exact schema and `249,994`-row match across `125` bounded batches. Although `REPACK (CONCURRENTLY)` wrote ~`401.8 MB` of WAL and temporarily raised the CDC slot's confirmed-flush WAL gap to `401,849,920` bytes, `pg2iceberg` drained the gap without duplicating or dropping any rows. Both runs ended with identical Iceberg file and record counts (`43` live data files, `251,536` data records, `17` live equality-delete files, `1,542` equality deletes). Project-only cleanup removed all `cdclab` containers, volumes and networks after each run without altering unrelated host containers.

### Table sizing for overlap

Idle sizing probes on `cdclab/postgres:19.0` showed that M1's `25,000`-row table (`7.1 MB`, `100` TOAST rows) completed `REPACK (CONCURRENTLY) public.orders` in `0.082 s`, which is shorter than a single `100 ms` inter-arrival period at `10.0 ops/s` and would fail to show write overlap. ## Limitations

- Single matched pair (`n=1`) on one Windows 11 Docker Desktop host. Tail latency comparisons (`p99`, `max`) over `n=45` ops in a `4.5 s` REPACK window have high variance; M3's three counterbalanced matched pairs are needed to distinguish host I/O noise from consistent REPACK effects.
- The `50 ms` progress/lock sampler did not observe the brief `catch-up` or `swapping relation files` (`AccessExclusiveLock`) phase between polls, and no workload write was caught waiting on `AccessExclusiveLock`. This indicates the final swap was brief under `10.0 ops/s`, but means M2 cannot report final-lock-specific latency figures.
- Only `30 s` of workload (~`300` writes, `259` dead tuples) preceded REPACK, so table bloat before REPACK was small (`-548.9 KB` TOAST reclaimed, `-196.6 KB` total). A heavily bloated table is not tested here.
- Automatic compaction in `pg2iceberg` remained disabled (`target_file_size: 0`), matching M0 and M1.
